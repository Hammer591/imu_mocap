## 2026-07-29~30 — ORB-SLAM3-ROS2 集成

**目标：** 集成 ORB-SLAM3-ROS2，通过 D435i 相机获取彩色流数据和相机空间轨迹。

**选型：** 对比 ORB-SLAM3 vs OpenVINS，选定 ORB-SLAM3-ROS2：

**选用仓库：** [gjcliff/ORB_SLAM3_ROS2](https://github.com/gjcliff/ORB_SLAM3_ROS2)

### 编译过程

- 禁用不必要的组件：Python 绑定、视频驱动、测试、示例

**2. ORB_SLAM3 核心库**

**4. ROS2 包装**
- `nav2_map_server` 不可用 → 移除 map 保存功能和相关 `find_package`
- `orb_alt` 节点 yaml-cpp 链接问题 → 禁用

### 运行时环境问题

**conda 冲突：**
- conda Python 3.14 与 ROS2 Humble 的 Python 3.10 C 扩展不兼容
- 每步操作前必须 `unset CONDA_DEFAULT_ENV CONDA_PREFIX CONDA_EXE`
- `export PATH="/usr/bin:$PATH"` 强制使用系统 Python

**PYTHONPATH 陷阱：**
- 设置 `PYTHONPATH` 指向覆盖层的 `dist-packages` 会破坏 ros2cli 包加载
- 原因是覆盖层没有 ros2cli，Python 优先找到覆盖层路径后不再回退到系统路径
- 解决方案：不设 PYTHONPATH，用 symlink 将 xacro 模块链接到用户 site-packages

**LD_LIBRARY_PATH：**
- `source /opt/ros/humble/setup.bash` 不自动设 `LD_LIBRARY_PATH`
- 必须显式 `export LD_LIBRARY_PATH="/opt/ros/humble/lib"` 否则 rclpy C 扩展找不到 librcl_action.so

### 源码修复（5 个）

所有修改在 `src/imu_mono_realsense.cpp`：

1. **IMU 数据不足时 return 导致帧全部丢弃**
   - 原代码 `if (vImuMeas.empty() && sensor_type_param == "imu-monocular") { return; }` 写在 while 循环内部
   - 前几秒 IMU 缓冲为空 → 所有图像被丢弃 → 视觉初始化失败
   - 改为始终调用 `TrackMonocular()`，ORB-SLAM3 内部会处理空 IMU 数据

2. **Tcw_ 被失败位姿覆盖**
   - `TrackMonocular` 失败时返回 identity（零位姿）
   - 原代码无条件写 `Tcw_.translation() = Tcw.translation()`
   - 修复：仅当 `GetTrackingState() == 3`（OK 状态）才更新 Tcw_

3. **纯单目模式不发布任何话题**
   - timer_callback 中条件为 `if (orb_slam3_system_->isImuInitialized())`
   - 纯单目模式下永远返回 false → RViz 中看不到任何数据
   - 修复：改为 `if (GetTrackingState() == 3 && have_valid_pose_)`

4. **Ctrl+C shutdown 崩溃**
   - `pcl::io::savePCDFileBinary` 在点云为空时抛 `pcl::IOException`
   - 修复：加 `if (live_pcl_cloud_.points.size() > 0)` 保护

5. **新增 have_valid_pose_ 成员变量**
   - 初始化为 false，跟踪成功时置 true
   - timer_callback 检查此标记后才发布，防止发布无效位姿

### D435i USB 不稳定问题

实际测试中 ORB-SLAM3 反复出现：
```
xioctl(VIDIOC_QBUF) failed when requesting new frame! fd: 24 error: No such device
```
相机 USB 连接在运行时断开，导致 SLAM 收不到图像 → 丢跟踪 → 反复重置。

即使纯单目模式能初始化（创建 ~116~329 个特征点），下一秒也因 USB 断开而丢失跟踪。

**结论：该问题为硬件问题（USB 线/口接触不良），非软件 bug。** 建议：
- 换 USB 3.0 口（蓝色）
- 换高质量 USB 线
- 避免通过 USB Hub 连接

### D435i USB 掉线问题（`VIDIOC_QBUF failed: No such device`）

- 相机运行中从 USB 总线消失（V4L2 设备节点在内核消失），realsense 自动重枚举后恢复
- USB 拓扑排查：D435i（usb4，5Gbps）与 STM32（usb3，12Mbps）挂在不同 root hub，物理独立，带宽差 400 倍，**不可能是串口抢相机**
- 关键发现：D435i 端口 `power/control=auto` —— **USB autosuspend 自动挂起**是周期性掉线的经典原因
- 建议：`udev 规则禁用 D435i autosuspend`（`ATTR{power/autosuspend}="0"`）

## 2026-07-31 — ⭐ imu_relay 与 ORB 冲突问题（本次重点）

### 现象

`record_slam_mocap.sh --duration 60 --monocular` 录制时 ORB-SLAM3 频繁异常/崩溃，而单独运行 `./run_orb_slam3.sh true true monocular` 完全正常。

### 排除法实验（关键）

| 实验 | 组成 | 结果 |
|------|------|------|
| 1 | 终端1 `run_orb_slam3.sh` + 终端2 `mocap_node` | ✅ ORB 完全正常 |
| 2 | 实验1 + 终端3 `imu_relay` | ❌ **ORB 立刻异常卡顿** |

**根因锁定：`imu_relay`（Python 节点）是唯一的冲突源。**

### 冲突机制分析

```
realsense2_camera (unite_imu_method=2, 200Hz IMU 合成流)
   │
   ├──→ ORB-SLAM3 (C++ 订阅者, BEST_EFFORT)
   └──→ imu_relay (Python 订阅者, BEST_EFFORT)   ← 问题源头
          └─ Python: 复制消息 + Madgwick 解算 + 发布 /imu0（全在 GIL 下）
```

- `unite_imu_method=2` 内部用单线程 syncer 合成 IMU 流
- 多一个 **Python 订阅者** → 驱动每次要给两个订阅者序列化消息，Python 侧处理慢会拖住驱动回调
- HID 传感器缓冲堆积 → IMU 帧延迟 → ORB 图像回调等 IMU 数据被卡住 → 卡顿/异常

### 为什么 mocap_node 不冲突

mocap_node 只打开 STM32 串口 `/dev/ttyACM0`，发布 `/*/imu` 话题，**完全不碰相机 IMU 话题**，与 ORB 无共享资源。实验 1 证实两者共存完全正常。

### 修复方案

`/imu0` 是冗余数据（Madgwick 算出的相机姿态，与 SLAM 轨迹重复），**从录制管线整体移除 imu_relay**：

1. `record_slam_mocap.sh` 删除 imu_relay 启动步骤（4步→3步）
2. 录制话题删除 `/imu0`，**保留原始 `/camera/camera/imu`**（这才是需要的 200Hz 原始相机 IMU）
3. 相机 IMU 数据离线处理即可（Madgwick 或 VIO 融合）

### 退出残留修复

录制脚本退出时 ORB 进程残留（ros2 launch 的子进程成孤儿）：
- 新增 `kill_tree()` 递归杀进程树
- pkill 兜底：按特征清理 `imu_mono_node_cpp` / `realsense2_camera_node` / `robot_state_publisher` / `static_transform_publisher` / `rviz2`
- 清理了此前累积的 18 个孤儿进程

### 最终状态

- ✅ `./record_slam_mocap.sh --duration 60 --monocular` **稳定录制**（无卡顿、无崩溃、退出干净）
- ✅ 录制的 bag 含：`/orb_odom` 相机轨迹、`/camera/camera/color/image_raw` 彩色流、`/camera/camera/imu` 原始相机 IMU、6 段身体 IMU、足底反力、TF

## 2026-07-31（续）— imu-monocular 修复与轨迹发布

### 根因发现：官方保护被删导致 SIGSEGV

对比 `git diff` 发现，之前为修复"IMU 数据不足丢帧"误删了官方关键保护：

**官方：**

**我们当时删掉了保护，无条件调用** → 空 `vImuMeas` 进入 ORB → `Not preintegrated measurement` → `inertial optimization` SIGSEGV。

**修复：** 恢复 `if (vImuMeas.size() > 1)` 保护 → **imu-monocular SIGSEGV 消除**（50 秒测试无崩溃）。

原版 `timer_callback` 用 `if (isImuInitialized())` 发布，但 monocular 模式该值永远 false（`mbImuInitialized` 只在 IMU 初始化时置 true）。我们改成了：
```cpp
if ((isImuInitialized() || sensor_type_param == "monocular") && have_valid_pose_)
```

### reset 问题的本质

`Tracking.cc:2169`：`if (!isImuInitialized() || !GetIniertialBA2()) → ResetActiveMap()`
- **IMU 初始化完成（VIBA2）之前，任何一帧跟踪丢失都触发整个地图重置**
- 初始化的脆弱窗口 = 原版需要 15 秒连续运动激励
- 运动不足 → `Not enough motion` / `bad imu flag` → reset

- 轨迹位置不变 = 录制时相机没动（静止时 IMU 预测冻结，正常行为）

## 2026-07-31（续）— FAST_IMU_INIT 移植分析（只分析，未移植）

**来源：** [lturing/ORB_SLAM3_FAST_IMU_INIT](https://github.com/lturing/ORB_SLAM3_FAST_IMU_INIT)

**问题背景：** imu-monocular 初始化脆弱（15 秒运动激励 + 概率性失败），容易 reset。

### 该项目的优化原理

**1. 融合两种快速 IMU 初始化算法（初始化 15秒 → 5秒单目）**

| 算法 | 原理 | 来源 |
|------|------|------|
| VIG-Init | SVD 线性求解重力+尺度（三步：solve_gravity_scale → solve_scale_ba_given_gravity → refine_scale_ba_via_gravity） | zju3dv (IROS 2019)，即 `ImuInitializer.cc` |
| imu_initialization | gyro bias 用 g2o InertialOptimization，解析解加速 | arXiv:2103.03389，即 `methods.h` / `polynomial.cc` |

**2. IMUMethod 配置切换（3 种方法并存）**
```cpp
enum IMUMethod { IMU_ORB_SLAM3=0, VIG_INIT=1, IMU_INITIALIZATION=2 };
```
- 配置项：`IMU.IMUMethod`（yaml）
- LocalMapping 按方法分派：原版 `InitializeIMU` / `VigInit` / `IMUAlign`

**3. 初始化触发条件放宽**
- `VigInit` 只需 `min_kf=15~20` 个关键帧 + 短时间跨度（注释掉了原版 `minTime` 检查）
- 用 g2o 求 bg（`InertialOptimization`，`bg.norm()>1` 判定失败）
- 初始化结果合理性检查：`scale<10`（单目）、`|ba|<3` → 不合格直接拒绝，避免坏初始化

**4. 关键认知：它没有改 reset 逻辑本身**
- `Tracking.cc` 的 `!isImuInitialized() || !GetIniertialBA2() → ResetActiveMap` 和原版相同
- 它靠**缩短脆弱窗口（15→5秒）+ 初始化更鲁棒**来概率性减少 reset

### VIG-Init 算法细节（`ImuInitializer.cc`）

三阶段求解（全在 `init_imu()` 内）：
1. **preintegrate()** — 用当前 bias 重积分所有关键帧预积分
2. **可观测性检查** — 平均位移 `<0.02` 或加速度方差 `<0.4` → 直接失败（运动不足，避免坏初始化）
3. **solve_gravity_scale()** — 构建线性方程组 `Cx=d`（含重力 G 和尺度 s），`JacobiSVD` 最小二乘解出 `gravity` 和 `scale`
4. **solve_scale_ba_given_gravity()** — 固定重力，再 SVD 解 `scale` 和 `ba`（加速度计 bias）
5. **refine_scale_ba_via_gravity()** — 3 次迭代精化（含重力切平面扰动 `s2_tangential_basis`），damp=0.1

### 移植到当前项目的可行性评估

| 项目 | 结论 |
|------|------|
| FAST_IMU 基础版本 | **较老 ORB-SLAM3**（System.h 缺 `isImuInitialized`/`GetInertialBA1/2`/`GetMapPCL`/`getPrettyFrame`） |
| 当前核心库 | 较新版本，有上述 API + `-mno-avx` + g2o Eigen 路径修复 |

| ROS2 包装兼容性 | 直接替换会编译失败（缺 API）；需补齐或增量移植 |

### 移植路径（未执行，供将来参考）

**方案 A（推荐）：增量移植到当前较新核心库**
1. 复制新增文件：`ImuInitializer.cc/h`、`polynomial.cc/h`、`imu_ceres.h`、`methods.h`

- 风险较高

- FAST_IMU_INIT 的价值 = **缩短 IMU 初始化脆弱窗口（15→5秒）+ 初始化更鲁棒**，间接减少 reset
